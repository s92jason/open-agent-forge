# 導讀：帶著 reviewer 讀懂這個 PR

分組回答「先看哪裡」，導讀回答「看的時候要知道什麼」。
reviewer 最花力氣的不是讀程式碼，而是從 diff 反推：作者想解決什麼、用什麼做法、這一段跟那一段怎麼接起來。
導讀把這些先講出來，讓他可以把力氣留給判斷對錯。

## 共通原則

- **讀者是懂這個專案、但沒看過這次變更的同事。** 語言與框架的常識不用解釋，只講這次變更。
  例外是「不查文件就不會知道」的函式庫行為：它是看懂某一行的關鍵時，用一句話帶過。
- **導讀是中性的說明，不是意見。** 有問題的地方寫成 finding；導讀裡不評價好壞，也不藏問題。
- **只寫你從 diff 與程式碼確認過的事。** 在這個 repo 裡無法確認的說法（外部系統或伺服器的行為、作者在 PR 描述裡的主張），
  集中寫進 `notes.assumptions`；導讀裡用「依 PR 描述」帶過就好，不用每一句都加但書。
- **同一件事只講一次。** 每件事有它該在的位置（見下表）；上一層講過的，下一層不要再講。
- **寧可少。** reviewer 在看到 diff 之前要讀的字越少越好。寫不出比 diff 本身更多的資訊就留空，不要湊字、不要湊數。
- 講得出具體的符號（`CouponRepository.getCoupons()`），不說「相關的方法」。

| 要講的事 | 寫在 |
|---|---|
| 這個 PR 為什麼要改、用什麼做法 | `guide.background`、`guide.approach` |
| 一個情境執行時的先後順序 | `guide.flow` |
| 這一組做了什麼、為什麼排在這裡 | 分組的 `summary` |
| 兩組之間怎麼接起來 | 分組的 `relations` |
| 要 reviewer 親自確認的事 | 分組的 `focus` |
| 某個檔案在這一組裡的角色 | 檔案的 `note` |
| 某一行為什麼這樣寫 | `annotations` |
| 你認為有問題的地方 | `findings` |
| 無法在這裡確認的前提 | `notes.assumptions` |

## 1. `guide`：整個 PR 的導讀

| 欄位 | 長度 | 寫什麼 |
|---|---|---|
| `background` | 1–3 句、約 100 字以內 | 改之前是什麼狀況、為什麼要改。來源是 PR 描述，以及被刪掉或被取代的程式碼。讀不到原因時，寫從 diff 看得出的現況，並註明「PR 沒有說明原因」 |
| `approach` | 2–4 句、約 150 字以內 | 這個 PR 的做法，用一條主線講完，並點出關鍵的設計決定（例如「快取放在 Repository，而不是 ViewModel」） |
| `flow` | 3–7 步，每步一句 | 挑一個最有代表性的情境，寫它從頭到尾怎麼流過這次變更的程式碼。每一步講出具體符號，並用 `group` 標出這一步屬於哪一組 |

- PR 裡有很多件事時，`approach` 只講最主要的一兩件與它們共通的做法，其餘交給各組的 `summary`；不要把每件事都塞進來把句子拉長。
- `flow` 是給讀者的一條線：照著它，分散在各組的檔案就接得起來。
- PR 只有一部分有明確的執行流程時，`flow` 只寫那一條，並在第一步點明它是哪一件事（「以上傳附件為例：…」）。
- 完全沒有執行流程的 PR（純重構、設定、文件、一包互不相關的小修改）就省略 `flow`，不要硬湊。

範例：

```json
"guide": {
  "background": "優惠券列表每次進入畫面都重新打 API，列表頁與結帳頁各打一次，慢而且浪費流量。",
  "approach": "在 `CouponRepository` 加一層以 userId 為 key 的記憶體快取，畫面只透過 Repository 取資料。快取放在 Repository，所以列表頁與結帳頁共用同一份。",
  "flow": [
    { "text": "使用者打開優惠券頁，`CouponViewModel.load()` 被呼叫", "group": "g3" },
    { "text": "`load()` 呼叫 `CouponRepository.getCoupons(userId)`", "group": "g2" },
    { "text": "Repository 先查快取；沒有才呼叫 `CouponApi.fetchCoupons()`，並把結果寫回快取", "group": "g2" },
    { "text": "結果轉成 `CouponUiState.Loaded`，由 `CouponScreen` 畫出列表", "group": "g3" }
  ]
}
```

## 2. 每一組的 `focus`：看這組時要確認什麼

0–3 條。它是**不論你的結論如何，人都應該親自看一眼的地方**，寫成可以對著 diff 回答的問題或檢查點。

- 好：「領券之後，快取有沒有被清掉？」「`userId` 為空字串時會發生什麼事？」
- 不好：「注意程式碼品質」「確認邏輯正確」

寫法：

- **你已經確認過答案時，把結果與依據一起寫出來**，reviewer 就只需要抽查，不用重做一次：
  「兩個畫面同時查詢會不會打兩次 API——已確認不會：`getCoupons()` 以 `Mutex` 保護，`CouponRepositoryTest` 有涵蓋。」
- 同一個點已經有 finding 時直接指過去（「快取的失效時機，見 f1」）；這時 finding 要自己給 `id`。
- **既有行為被改變、可能影響呼叫端時**（例如舊方法現在多了一道驗證），一定要有一條 `focus` 請 reviewer 確認影響範圍。
  你判斷它會造成問題時，再另外寫成 finding。
- 沒有值得人確認的事就不寫，不要為了每一組都有而湊。純機械式變更的那一組，一條「確認沒有夾帶邏輯變更」就夠。

## 3. 檔案的 `note` 與 `skim`

分組的 `files` 可以直接寫路徑，也可以寫成物件，替檔案加一句說明：

```json
"files": [
  "domain/model/Coupon.kt",
  { "path": "data/CouponRepository.kt", "note": "這組的核心：加上快取，查詢先走快取" },
  { "path": "di/DataModule.kt", "note": "只是把新的建構子參數接上", "skim": true }
]
```

- **`note`**：一句話，盡量短（大約 40 個中文字，識別字不計）。寫**從 diff 第一眼看不出來的事**：
  這個檔案在這一組裡的角色、它為什麼要跟著改、該注意哪一段。
  不要只寫「新增 `X()`」「修改了 Y」——那是 diff 自己會說的。通常只有一部分檔案需要 `note`。
- **`skim: true`**：給**量大、但不用逐行讀**的檔案——改名、搬移、import、格式化、產生的程式碼、呼叫端機械式地跟著改。
  頁面會標上「可快速掃過」並預設收合。
  - 很小的變更（加一個欄位、一個常數）不用標：它本來就一眼看完，收合反而多一個動作。
  - 含有邏輯變更、或你在上面放了 finding 或註解的檔案不要標。
  - 一個檔案大部分是機械式變更、只有一處要看時，不要標 `skim`，改用一則註解指出那一處。

## 4. `annotations`：diff 行內的導讀註解

放在 diff 某一行旁邊的說明，格式和 finding 一樣用 `path`、`line`、`side`、`end_line` 定位，內容寫在 `text`。

適合放註解的地方：

- **關鍵邏輯所在**：「這次變更的核心在這裡：先查快取，沒有才打 API。」
- **不看上下文會看不懂的地方**：「`retryCount` 從 3 改成 0，是因為重試已經移到 `HttpClient` 那一層（第 1 組）。」
- **容易誤會的寫法**：「這裡刻意不用 `distinct()`：同一張券可以領多次。」
- **大檔案裡真正要看的那一段**：「這個檔案其餘的變更都是改名，只有這個函式的邏輯有變。」
- **被刪掉的程式碼為什麼可以刪**（`"side": "old"`，行號填舊行號）：「這兩個分支原本只做 token 檢查；檢查移到伺服器端之後整段拿掉。」

規則：

- 每則 1–2 句。**不要重述程式碼字面上的意思**（「這一行把 `x` 設成 1」）；要寫的是從這一行看不出來的事。
- 每組 0–4 則，整個 PR 通常不超過 15 則；小 PR 一兩則就夠。註解太多，讀者就不看了。
- 程式碼裡的註解已經把原因講清楚時，不用再放。
- 已經在 `summary`、`note`、`relations` 或 `flow` 講過的事，不要再用註解講一次。
- 同一行已經有 finding 把事情講清楚時，不用再放註解。
- 行號的填法與 finding 相同（見 `analysis-schema.md` 的「行號怎麼填」）。對不上 diff 的註解會被移到檔案開頭並記一筆警告。

## 第 2 輪以後

- 導讀描述的是 PR **目前**的樣子：沿用上一輪仍然正確的內容，只改有變的部分。
- 這一輪新增的變更，在相關的檔案放一則註解，說明「這一輪改了什麼」，例如「這一輪新增：領券成功後清掉快取（回應上一輪的 f1）」。
