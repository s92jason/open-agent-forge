# 分組與閱讀順序

PR 頁面預設依資料夾列出檔案，讀的人得自己在腦中把「這個 interface 的實作在哪、誰呼叫它」接起來，
檔案一多就會疲乏。分組的目的是**替讀者把這些連結先接好**：照著順序讀，每一組都只用到前面已經看過的東西。

## 怎麼分組

1. **一組是一個邏輯變更，不是一個資料夾。**
   同一個功能的 model、repository、ViewModel 分散在不同目錄是常態；把「為了同一件事而改」的檔案放一起。
2. **PR 裡有多件獨立的事，就先按事情切。**
   例如「新增優惠券列表」與「順手修了登入的 crash」是兩件事，各自成組，不要混在同一條依賴鏈裡。
3. **每組 2–8 個檔案、整個 PR 3–8 組是常見的樣子，不是規則。**
   第 1 條優先：不要為了湊數把不相關的變更併成一組，也不要為了拆組把同一件事切開。
   單組超過 10 個檔案就再切；只有一兩個檔案的小 PR 分一組就好。
   PR 是一包互不相關的小修改時，各自成組，單一檔案的組也可以；超過 10 組時，把最零碎的幾件集中成一組「零星調整」，在 summary 逐項列出各是什麼。
   「零星調整」不受單組 10 個檔案的限制（組數的上限優先），排在機械式變更那一組的前面。
4. **一個檔案同時屬於兩件事時，放進它主要變更所在的那一組**，並在另一組的 summary 提到它。
   「主要」看的是內容，不是行數：以 reviewer 最需要理解的那個變更為準。
   一個檔案是好幾件事共同的基礎時（例如共用的 client、base class），讓它自成一組排在最前面，
   標題直接列出它支撐的那幾件事，並用註解標出每件事在檔案裡的位置。
5. **機械式變更集中放最後一組。**
   大量改名、格式化、import 調整、產生的程式碼——標題寫明是機械式變更，summary 說「可以快速掃過」以及有沒有例外需要細看。
   個別檔案標上 `skim: true`（見 `reading-guide.md`），頁面會預設把它們收合。
6. **測試跟著它測的對象。**
   測試檔放在同一組的最後，讀完實作馬上看測試。只有測試本身就是這次變更的主體（補測試的 PR）時才獨立成組。
   一個測試檔涵蓋好幾組時，放在它主要驗證的行為所在的那一組，並在另一組的 `relations` 提一句。
7. **沒有納入審查的檔案也要分組。**
   圖片、產物、lock 檔跟著用到它的那一組；真的沒有歸屬就放機械式變更那一組。漏掉的會被自動丟進「未分組」。

## 怎麼排順序

原則只有一個：**被依賴的在前面**，讓讀者先認識詞彙，再看用到它的地方。

沒有更好的依據時，照這個順序排（組與組之間、組內檔案之間都適用）。以下以 Android 專案為例：

1. 資料模型、介面、常數——後面所有東西的詞彙
2. 資料來源——API、資料庫、Repository
3. 領域邏輯——UseCase、Handler、狀態機
4. 畫面狀態——ViewModel、Presenter、UI state
5. 畫面——Compose、XML、Fragment、Activity
6. 接線——DI、導航、設定、manifest
7. 測試（若獨立成組）
8. 機械式變更

其他類型的專案套用同一個原則：共用的型別與基礎設施 → 用到它們的功能（依彼此的依賴順序）→ 測試 → 機械式變更。
互不相依的幾組之間，把風險最高或變更最大的排前面。

如果這個 PR 的**主要目的**是修一個 bug，把修正本身放第一組，再放因為它而連帶調整的部分——讀者最想先看的是那個修正。
功能 PR 裡順手修的 bug 不適用這一條，照依賴順序排。

## 標題與 summary

- **標題**用這次變更的領域語言：寫「優惠券查詢與快取」，不寫「Repository 層」。
- **summary** 寫 1–2 句：這組做了什麼，以及它為什麼排在這個位置。
  - 好：「API 新增查詢端點，Repository 加上以 userId 為 key 的記憶體快取。畫面那一組會透過它取資料。」
  - 不好：「修改了 3 個檔案。」
- 審查時要注意的事不寫在 summary，寫成這一組的 `focus`（見 `reading-guide.md`）。

## relations：把跨組的連結寫出來

讀者最難自己建立的是**跨組**的關係。每組列出它與其他組的接點，一則一句話，講得出具體的符號：

- 「回傳第 1 組的 `Coupon`」
- 「`load()` 呼叫第 2 組的 `getCoupons()`」
- 「訂閱第 3 組的 `uiState`」

每個接點只寫一次，寫在**後面**（用到別人）的那一組，指向它依賴的前面那一組；不用在兩組各寫一次。
同一對分組之間有好幾個接點時可以寫好幾則，一則講一個。
只寫真的存在於這次變更裡的關係。沒有就留空陣列，不要湊數。

## 第 2 輪以後

- 沿用上一輪的分組與組名，讀者已經熟悉那個結構。
- 新增的檔案放進最相關的既有分組；只有出現全新的一件事時才加新組。
- 上一輪的某一組若整組都已不在變更裡，就拿掉。
