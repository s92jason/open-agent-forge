# Model / Effort / Permission Mode 判定 Rubric

> task-brief 用這份 rubric 為「新 session」選 model、effort、permission mode。
> 三個軸互相獨立，各自判定；每個選擇都必須能指回下方「訊號清單」裡的編號。
> **只用可觀察的訊號**：看得到的需求文字、repo 掃描結果、git 狀態。不用「感覺很難」「應該很複雜」這類推測。

---

## 0. 官方定位（判定的基準）

以下摘自 Claude Code 官方文件 [Model configuration](https://code.claude.com/docs/en/model-config)、
[Permission modes](https://code.claude.com/docs/en/permission-modes)，2026-10-14 查證。官方文件更新時以官方為準，並回頭修這一節。

### Model 別名

| 別名 | 官方定位 |
|---|---|
| `fable` | 最難、最長時間的任務；官方說適合「超過一次坐下就能完成」的工作，例如根因調查、事故除錯、架構決策 |
| `opus` | 複雜推理任務 |
| `sonnet` | 日常 coding 任務 |
| `haiku` | 快速、有效率，適合簡單任務 |

- 一律寫別名，不寫完整 model id——別名會跟著官方指向最新版本。
- `default`、`best`、`opusplan`、`[1m]` 變體不在本 rubric 的輸出範圍內。

### Effort 等級

| 等級 | 官方描述 |
|---|---|
| `low` | 快速往返、使用者會逐項檢視結果，例如腦力激盪、初稿、改名這類小改動 |
| `medium` | 範圍清楚的日常工程工作；Opus 5.5 / Sonnet 5.5 / Haiku 5.5 的預設值 |
| `high` | 需要驗證、或邊界情況多的工作，例如在既有 codebase 修 bug |
| `xhigh` | 更深的推理，token 花費更高 |
| `max` | 希望 Claude 不需要你就自己做到底的困難問題，例如找資安漏洞；官方提醒可能報酬遞減、容易想太多，先試再大量採用 |

- 目前各別名指向的最新版本（Fable 5.1、Opus 5.5、Sonnet 5.5、Haiku 5.5）都支援全部五級。
- 模型不支援所選等級時，Claude Code 會改用「不超過所選等級的最高支援等級」。

### Permission mode

| mode | 不需詢問就能做的事（官方） | 官方建議情境 |
|---|---|---|
| `plan` | 只讀（auto mode 可用時，另含分類器核准的指令） | 動手前先探索 codebase |
| `default` | 只讀 | 每個動作都要自己審 |
| `acceptEdits` | 讀、檔案編輯、常見檔案系統指令（`mkdir`、`touch`、`mv`、`cp` 等） | 信任編輯、但指令仍要審 |
| `auto` | 全部，背景有安全檢查 | 長任務、減少確認疲勞 |

`auto` 的前提（官方）：Claude Code v2.1.283 起是互動 session 的內建起始模式；model 需為 Opus 4.6+、Sonnet 4.6+、Haiku 5.5 或 Fable（Anthropic API）；組織管理員可用 `permissions.disableAutoMode` 關閉。不滿足時 session 會以 Manual（default）開始。

## 1. 訊號清單

判定前先把需求與掃描結果對到下列訊號，記下編號。輸出的「觸發訊號」欄位只能列這裡的編號與一句實際觀察。

### 範圍（S）

| 編號 | 訊號 | 怎麼觀察 |
|---|---|---|
| S0 | 需求點名的既有對象在目前 repo 找不到，且需求是修改而非新建 | Grep / Glob 需求裡的類別、檔名、模組名皆無命中程式碼（只命中文件範例不算） |
| S1 | 預估改動 1–2 個檔，且一句話能完整描述改動 | 需求文字點名檔案或對象；Grep 命中 ≤ 2 檔 |
| S2 | 預估改動 3–10 個檔，集中在單一模組 | Grep 需求點名的類別 / 函式，命中檔案落在同一個目錄或模組 |
| S3 | 預估改動跨 2 個以上模組，或超過 10 個檔 | 命中檔案分散在多個模組；或需求本身就是「整個專案 / 多模組」 |
| S4 | 從零建立（目前 repo 沒有對應的程式碼） | 需求點名的對象在 repo 中 Grep 不到，且需求是新建而非修改 |
| S5 | 需求的技術棧與掃描的 repo 不符 | 需求點名的語言、平台或框架（例如 Android、iOS、Go）在建置檔與 git 追蹤的檔案中都找不到；只出現在文件範例不算 |

**同名檔規則**：需求點名的名稱同時命中多個同名檔（例如 repo 根與各子目錄都有 `README.md`）時，範圍以**最接近 repo 根的那一份**計，其餘同名檔列入 prompt 的「待確認」，不算進 S1–S3 的檔數。理由：需求用單數名稱時，字面上指的是一份；全部算進去會把一件小事誤判成跨模組。

### 判斷（J）

| 編號 | 訊號 | 怎麼觀察 |
|---|---|---|
| J1 | 機械性改動，沒有做法上的選擇 | 錯字、改名、格式、版本號字串、照抄式修改 |
| J2 | 有先例可循 | repo 裡有同類的既有實作可以模仿（Grep 到相似命名或結構） |
| J3 | 需要在 2 個以上可行做法中取捨，且影響既有結構 | 需求含「重構」「抽象」「可測試」「拆分」「解耦」等，會改介面、模組邊界或資料流 |
| J4 | 要下架構決定，且會約束之後多個 session 的工作 | 需求含「規劃」「架構」「從零」「技術選型」「模組切分」 |
| J5 | 必須保持既有行為不變（等價改動） | 需求是重構、搬移、抽換實作 |

### 探索（E）

| 編號 | 訊號 | 怎麼觀察 |
|---|---|---|
| E1 | 不需讀其他 code 就能開工 | 改動對象本身就是全部脈絡（文件、字串） |
| E2 | 需讀少量 code（≤ 10 檔）才能開工 | 需要看呼叫端、相依的少數檔案 |
| E3 | 需大量讀 code 或比較多個方案才能開工 | 呼叫端分散、或需要先調查才知道怎麼做 |
| E4 | 驗收要靠反覆執行與回頭修正 | 需求要求測試通過、行為等價、效能達標 |

### 可逆性（R）

| 編號 | 訊號 | 怎麼觀察 |
|---|---|---|
| R1 | 目前目錄是 git repo，工作區乾淨 | `git status --porcelain` 無輸出 |
| R2 | 不是 git repo，或工作區有未 commit 的改動 | `git rev-parse` 失敗，或 `git status --porcelain` 有輸出 |
| R3 | 改動會碰到 git 追蹤以外的狀態 | 需求含資料庫 migration、刪除資料、部署、push、發布、改系統或全域設定、呼叫外部服務 |
| R4 | repo 有可執行的測試 | 找到測試目錄或測試指令（`tests/`、`src/test`、`*_test.*`、`package.json` 的 `test` script、`./gradlew test`、CLAUDE.md 的測試章節） |
| R5 | 需求要反覆執行 build / test 指令 | 驗收條件需要跑測試或建置 |

## 2. 判定規則

每個軸**由上往下，第一個成立的就選**。不要跳級、不要折衷。

### 軸一：Model —— 判斷密度相對輸出量

判斷越密、輸出越少，越該用強模型；判斷少、輸出多，用快模型。

| 順序 | 選 | 成立條件 |
|---|---|---|
| 1 | `fable` | J4，且（S3 或 S4） |
| 2 | `opus` | J3 或 J4；或 J5 且 E3 以上；或 S3 |
| 3 | `sonnet` | 需要寫或改程式邏輯（不是 J1），且不符合上面兩列 |
| 4 | `haiku` | J1 且 S1 且 E1 |

- 第 3、4 列都不成立時（例如 J1 但 S2），選 `sonnet`。
- 需求同時落在兩列之間時，以表格順序為準——規則本身已經偏向較強的模型，因為選錯模型的代價是整個 session。

### 軸二：Effort —— 需要探索與回頭修正的程度

| 順序 | 選 | 成立條件 |
|---|---|---|
| 1 | `max` | 只在需求明說「不需要我、自己做到底」，且屬於窮舉式問題（例如找資安漏洞）時才選；其他情況一律不選 |
| 2 | `xhigh` | E3，且（J4 或 S4） |
| 3 | `high` | E3 或 E4；或 J5 |
| 4 | `medium` | E2 |
| 5 | `low` | E1 且 J1 |

組合檢查（不成立就調整，並在理由說明）：

- `haiku` 只配 `low` 或 `medium`；判到更高時，回頭把 model 升一級。
- `fable` 至少配 `high`。

### 軸三：Permission mode —— 改動的可逆性與範圍

| 順序 | 選 | 成立條件 |
|---|---|---|
| 1 | `plan` | J4；或 R3；或 S3 / S4 且產出需要先對齊方向 |
| 2 | `default` | R2，且 R2 是「不是 git repo」 |
| 3 | `auto` | R1 且 R4 且 R5，且改動範圍 S2 以上 |
| 4 | `acceptEdits` | 以上都不成立 |

- **未 commit 的改動（R2 的另一種情況）**：不直接判 `default`，而是把第 3、4 列的結果降一級（`auto` → `acceptEdits`，`acceptEdits` → `default`），並在理由寫「先 commit 後可回升為 X」。理由：新 session 的改動會和現有改動混在一起，無法一鍵回復。
- **S0（點名對象找不到）**：範圍無法觀察，第 3 列（`auto`）視為不成立；model 與 effort 只依 J / E 訊號判定。
- **S0 或 S5（目標不在掃描的 repo）**：使用者沒有指定目標目錄時，交接包開頭要提示「目標可能在別的目錄」，並給出指定目錄重跑的寫法（`/task-brief <需求> --cwd <目標目錄>`）。S4 且 S5（在別處從零建立）時，同時把「新專案要建在哪」放進「待確認」第一題。
- 選 `auto` 時，在理由加註官方前提（版本與 model 支援）；使用者的環境不支援時會自動以 Manual 開始。

## 3. 輸出要求

每個軸輸出三樣東西：

1. **選擇**：別名或等級，原樣（`opus`、`high`、`plan`）
2. **一句理由**：說「因為觀察到什麼，所以選這個」，不要重述表格
3. **觸發訊號**：列編號＋實際觀察，例如 `S2：UserRepository 在 data/ 下命中 4 檔`

不允許的理由寫法：

- 「這是複雜任務」——沒有指出觀察
- 「保險起見」——沒有對到規則
- 引用表格以外的訊號
