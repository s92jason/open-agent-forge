Claude Code Skill

把 Axure / Figma 設計稿，
變成 RD、QA、AI 都能讀的工程規格

它讀你的設計連結，自動整理成一份結構化的 FEATURE-SPEC.md—— 包含流程圖、畫面狀態、API 欄位、業務規則與驗收條件。 讓接手的工程師在 5～10 分鐘內建立正確認知，不必再從零讀設計稿。

▶ 看怎麼用 它為什麼做得到？
一句話：機械的事（讀取、解析設計工具的私有格式）交給程式； 判斷的事（看懂、整理、寫成規格）交給 AI。中間用一份乾淨的資料接起來。

這是什麼 · 解決什麼問題

設計稿到工程實作之間，有一段「沒人想做、又最容易出錯」的整理工

設計師交付的是 Axure 流程圖和 Figma 畫面；工程師需要的是「哪些畫面、什麼狀態、 呼叫哪些 API、什麼條件下做什麼」。這中間的翻譯，過去靠人逐頁讀、逐張比對， 耗時、易漏、且每個人理解都不一樣。

😮‍💨 沒有它的時候

  • 新人接手要花半天到一天讀設計稿才看懂功能
  • 流程分支、錯誤碼、邊界情境散落各處，容易漏
  • 規格文件靠人手寫，常常寫一半、過時、與 code 對不上
  • RD、QA、PM 各看各的，認知不一致
  • 「這個欄位前端到底用不用？」反覆來回確認

✨ 有了它之後

  • 貼上設計連結，幾分鐘內得到結構化規格草稿
  • 流程圖、狀態表、錯誤碼表自動整理、集中呈現
  • 文件進 git，可 review、可 diff、可追溯版本
  • 同一份文件 RD / QA / AI 共讀，認知一致
  • 欄位「前端用 / 不用」明確分兩欄，不再來回問

產出長什麼樣

一份文件，兩個區域：人類快讀區 + AI 查找區

文件刻意分成兩半。上半部讓工程師 5～10 分鐘建立認知；下半部是結構化工程資料， 給 AI Agent 與深度查找用。每條規則只在一個章節完整定義，其他章節只引用—— 避免同一件事在多處重複、又互相矛盾。

為什麼它做得到

它讀回來的資料，看起來只是「一堆文字」——為什麼能變成精確的流程？

這是最多人好奇的一點。程式從設計稿抓回來的，乍看只是把網頁上的字攤平成清單， 人類很難看出流程關係。但關鍵在於：丟失的是「箭頭的畫法」，沒丟的是「箭頭上的標籤」—— 而對 AI 來說，標籤就足夠把整張圖重新接回來。背後有五個機制：

箭頭丟了，但箭頭上的字還在

設計師畫的流程圖被攤平後，連線不見了，但每個方框、每個條件的文字都還在， 有時連箭頭都原封不動，例如 手機已註冊 →登入流程。

決策、條件、結果，本身就是文字

流程圖的零件全在清單裡：決策（是否綁定成功）、條件（RETURNCODE=0000）、 結果（綁定成功 / 失敗）。AI 把它們重新連成判斷分支。

畫面的「命名」本身就是一套分類

像 個人權益_開通_介紹頁_error 這種命名，即使內文是空的， 名字就帶了畫面、狀態、順序、裝置（iOS / Android）資訊，AI 直接解讀。

兩個來源互相對照、互相補完

Axure 給「邏輯」、Figma 給「畫面」。同一個錯誤碼在 Axure 是一列表格、 在 Figma 是一個錯誤畫面——兩邊都指向同一件事，AI 對它的信心就拉滿。

AI 自己「看過很多類似流程」

註冊、綁定、同意條款這類流程，AI 學過成千上萬個，腦中有現成骨架。 它把你資料裡的碎片，卡進骨架對應的位置，補上沒明說的部分——再把不確定的標出來。

💡 一個好懂的比喻

想像一盒被打散的拼圖：每一片上面還印著圖案，只是被倒在桌上。 人一次只能拿幾片在手上比對，拼到後面就忘了前面； AI 能「同時看見全部的片」，並且一次計算每一片和其他所有片的關聯， 所以它能快速把整張圖拼回來。攤平的資料對人是負擔，對 AI 剛好是最擅長的形式。

我要怎麼信任它

它的設計核心是「重建，而不是偽造」

AI 最讓人擔心的是「自信地編造」。這個 skill 用一整套機制確保它誠實—— 不確定就標記、衝突有規則、關鍵問題會停下來問人。

✓

不確定的，明確標記

沒把握的內容會標成「待確認事項」並集中在文件末尾，絕不偽裝成已定稿。

✓

關鍵問題，停下來問人

產出草稿後有一道強制問答關卡：有疑問就列清單給你確認，確認過才算完成。

✓

來源衝突，有固定優先序

流程以 Axure 為準、畫面以 Figma 為準、資料以 API 為準——不隨機、可預期。

✓

產出是純文字，可審可追

輸出是 Markdown，進 git 版控，任何人都能 review、diff、回溯每次變更。

✓

機密不落地

Figma token、Axure access code 存在作業系統的安全憑證庫， 絕不寫進專案、規格文件或紀錄。

✓

能與程式碼雙向對齊

功能完成後可用「程式碼同步模式」反向核對，找出 spec 與實際 code 不一致之處。

誠實揭露它的邊界：它是「重建」不是「精準解析」——當來源沒有明確箭頭時， AI 會用常見流程推論方向，有可能接反分支。這正是「停下來問人」機制存在的原因： 把不確定攤開讓人覆核，而不是悶著頭猜。它定位是 RD/QA/AI 的工程規格，不取代 PM 的 PRD。

三種模式

不只能「從零建立」，還能持續維護、與程式碼對齊

規格是活文件。這個 skill 支援三種使用情境，讓文件能跟著專案一起長大。

Create · 建立

從零產一份新規格

還沒有規格文件時，提供 Axure / Figma / API，一步步收集後產出完整 spec。 業務規則欄位先留「待回填」標記。

Update · 更新

改版時局部更新

已有規格、設計改版時，用菜單挑要動的部分（Axure / Figma / API / 待確認事項）， 只覆寫受影響章節，不暴力整份重寫。

Code Sync · 同步

用程式碼反向校準

功能收尾時，掃描實際程式碼，回填「實作位置」、找出 code 與 spec 的不一致與過時段落， 列報告給你勾選才寫回。

適用 · 不適用

什麼時候該用它，什麼時候不該

✅ 適合

  • 要把 Axure + Figma 的設計，整理成 RD / QA 共讀的工程規格
  • 新功能要建立 canonical feature spec
  • 改版後要更新既有規格文件
  • 功能收尾，要讓 spec 對齊目前程式碼

🚫 不適合

  • 只想做 PRD / 商業敘事 / PM 文件
  • 只有零碎想法，還沒有 Axure 與 Figma
  • 純 bug fix、純重構、純 commit message
  • 只想問某段程式碼邏輯，不需要建立或更新規格

常見問題

FAQ

它會不會自己亂編內容？
不會默默編造。沒把握的地方會標成「待確認事項」並停下來問你； 來源衝突時依固定優先序處理並標記。它的設計目標是「重建你給的資料」， 而不是「無中生有」。真正不確定的推論（例如流程分支方向）會被列出來請你覆核。
我的 Figma token / Axure 密碼安全嗎？
安全。憑證存在你電腦作業系統的安全憑證庫（Keychain）， 絕不會寫進專案程式碼、規格文件、變更紀錄或任何輸出文字裡。
只有 Figma、沒有 Axure（或反過來）可以用嗎？
可以。至少要有一個設計來源。缺少的那一邊，對應章節會標記「來源未提供」， 文件狀態最多到「進行中」，不會標成「可交付」。兩者都缺則只會產出標記為草稿的骨架。
不懂程式的人（PM / QA / 設計）看得懂產出嗎？
看得懂。文件上半部「人類快讀區」就是為非工程角色設計的—— 功能簡介、流程圖、畫面狀態、驗收條件，都用結構化但白話的方式呈現。 下半部偏技術的附錄則是給 RD 與 AI 深度查找用。
產出之後還要花多少人力？
它產的是「高品質草稿 + 明確的待確認清單」。你主要的工作是回答那幾個它停下來問的問題， 以及覆核推論部分。比起從零手寫一份規格，省下的是大部分的整理與排版工。
規格會不會做完就過時、跟程式碼對不上？
這正是「程式碼同步模式」要解決的。功能完成後，它能掃描實際程式碼， 回填規格裡的「實作位置」、找出與程式碼不一致或已過時的段落，列報告讓你勾選更新。 規格因此能跟程式碼雙向收斂。
